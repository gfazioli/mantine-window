**When to use which.** Reach for the core `FloatingWindow` for a light draggable panel you style yourself — a floating toolbar, a chat box, a picture-in-picture player — when you would rather not add a dependency. Reach for `Window` when you want desktop-style windows: a title bar with its controls, resizing from any edge, sizes in viewport units or percentages that follow the breakpoints, a window confined to a container, position and size kept across reloads with `persistState`, and several windows arranged together with `Window.Group`. Reach for its [headless hook](#headless-hook) when you want that same geometry on an element of your own.

## Usage

The `Window` component allows you to create draggable and resizable windows within your application. It provides a familiar desktop-like experience for users. You can customize the appearance and behavior of the windows using various props.

> **Note:**
>
> Usually, you would want to use the `Window` component within a portal to avoid layout issues. However, if you want the window to be constrained within a specific container, you can set the `withinPortal` prop to `false` and the container should have `position: relative` style.
>
> For example, in the demos below, the `Window` component is rendered relative to its parent container which has `position: relative` style.

## Position and Size

Set the initial position and size of the window using `defaultX`, `defaultY`, `defaultWidth`, and `defaultHeight` props. These values are used when the window is first rendered and can be modified by the user via drag and resize.

<Demo data={demos.positionAndSize} />

## Controlled Position and Size

For full external control, use the `x`, `y`, `width`, and `height` props. When these are set, the component does not manage that value internally — your state drives it. Combine with `onPositionChange` and `onSizeChange` to sync state after user interactions.

You can also mix controlled and uncontrolled: for example, control only `x` and `y` while letting `width` and `height` remain uncontrolled via `defaultWidth` and `defaultHeight`.

<Demo data={demos.controlledPosition} />

## Within Portal vs Container

The `withinPortal` prop controls how the window is positioned. When `withinPortal={true}` (default), the window uses fixed positioning relative to the viewport. When `withinPortal={false}`, it uses absolute positioning relative to its parent container.

**Fixed positioning (withinPortal=true):**

- Window stays in place when scrolling
- Positioned relative to the browser viewport
- Best for modals and overlays

**Absolute positioning (withinPortal=false):**

- Window is constrained within parent container
- Parent must have `position: relative`
- Window cannot be dragged or resized outside container boundaries
- Best for embedded UI components

<Demo data={demos.withinPortal} />

## Unit Types

Position and size props support three unit types:

- **Pixels** (number): Fixed pixel values, e.g. `defaultX={100}`
- **Viewport units** (string): `vw` for viewport width, `vh` for viewport height, e.g. `defaultX="10vw"`
- **Percentages** (string): Relative to the reference container, e.g. `defaultX="20%"`

**Understanding Unit References:**

- **`vw/vh`**: Always relative to the **browser viewport**, regardless of `withinPortal` setting
- **`%`**: With `withinPortal={true}` (default) relative to the **viewport**; with `withinPortal={false}` relative to the **parent container**
- **Pixels**: Always **fixed**, regardless of `withinPortal` setting

You can mix different unit types freely on the same component.

## Axis Lock

Set `axis="x"` or `axis="y"` to restrict dragging to one direction: a window that slides along a dock, a panel that only moves up and down. The locked coordinate stays where the gesture started, while the free one is still kept inside the viewport, the container or `dragBounds`.

Only the user's drag is locked. A controlled `x` / `y`, the layouts of the tools menu and of `Window.Group` still move the window anywhere.

## Touch Screens and Small Boundaries

On a phone or a tablet, a window behaves as a finger expects:

- A swipe on content that overflows scrolls it, because a finger has no wheel. A swipe on the title bar, or on content that fits, drags the window as before. The mouse is unchanged: it still drags from anywhere and scrolls with the wheel.
- Each window follows only the finger that pressed it, so a second finger resting on another window does not drag that one too.
- The resize handles and the title-bar buttons get bigger hit areas on a coarse pointer, and the buttons show their glyphs, since there is no hover to reveal them.

`keepInBounds` (on by default) keeps every window reachable inside its boundary, the viewport or its container:

- When the boundary is measured, and whenever it or the window changes size (a phone rotating, a browser window or a container getting narrower, a collapsed window opening), a window that sticks out moves back inside it, and one larger than the boundary shrinks to fit. A collapsed window keeps its expanded height until it opens.
- `dragBounds` can only narrow the boundary: bounds written for a wide screen no longer let a window out of a phone's.
- Resizing with the pointer stops at the boundary, the viewport included, as keyboard resizing does.

Set `keepInBounds={false}` for the 3.3 behavior, for example to let a window hide partly off-screen through `dragBounds`. Moves made from code (a controlled `x` / `y`, the layouts) are never restricted.

By default, the window content is wrapped in a `ScrollArea` component. Set `withScrollArea={false}` to disable it — content that overflows will be clipped instead of scrollable. This is useful when your content already provides its own scrolling mechanism or when the `ScrollArea` interferes with the inner layout.

## Controls Position

The window title bar buttons (close, collapse, tools) default to the left side (macOS style). Set `controlsPosition="right"` to move them to the right side (Windows style). The button order is automatically reversed when positioned on the right — close moves to the far right, matching platform conventions.

For full control over button ordering, use the `controlsOrder` prop with an array of `'close'`, `'collapse'`, and `'tools'` in your desired sequence. When `controlsOrder` is set, it overrides the automatic ordering.

<Demo data={demos.controlsPositionDemo} />

## Full Size Resize Handles

By default, resize handles (top, bottom, left, right) are centered and have a limited size (40px). Setting `fullSizeResizeHandles={true}` makes these handles span the entire width or height of the window edge, providing a larger interaction area.

<Demo data={demos.fullSizeHandles} />

## Keyboard Resizing

Every resizable window has one resize handle that takes keyboard focus: the bottom-right corner, or the right edge when the window is collapsed or `resizable="horizontal"`, or the bottom edge with `resizable="vertical"`. One tab stop per window: the other seven handles stay pointer-only. With the handle focused:

- the arrow keys move its edge by `resizeStep` pixels (default `10`), and Shift + arrows by `resizeShiftStep` (default `50`);
- Home takes the window to its min size, and End to its max size.

No key ever takes the edge past the viewport or the container: there the edge wins over the min and max sizes, as it does when you resize with the pointer. End without a max size therefore stops at that edge.

The arrows are physical, as in the WAI-ARIA window splitter pattern: the window is placed with `left` and `top`, so in a right-to-left layout too the right arrow moves the right edge to the right.

The handle is a WAI-ARIA `separator`. Screen readers announce its name, `resizeHandleLabel` (default `'Resize window'`), and its value: the width, or the height on the bottom edge, between `aria-valuemin` and `aria-valuemax`. On the corner, which changes both, `aria-valuetext` reads the width × height. While it has keyboard focus the handle is drawn in the primary color and the window is outlined.

Each key press is a complete resize gesture: it brings the window to the front, fires `onResizeStart`, `onSizeChange` and `onResizeEnd` like a pointer resize, and is saved by `persistState`. Set `withKeyboardResize={false}` to keep every handle pointer-only.

<Demo data={demos.keyboardResize} />

## Callbacks

Use `onPositionChange` and `onSizeChange` callbacks to respond to window movements and resize operations. These callbacks receive the current position or size as pixel values.

<Demo data={demos.callbacks} />

### Drag and Resize Lifecycle

`onPositionChange` and `onSizeChange` fire continuously, on every frame of a gesture. Four more callbacks mark its edges instead: `onDragStart`, `onDragEnd`, `onResizeStart` and `onResizeEnd`. They mirror the set that Mantine core's `FloatingWindow` exposes.

The edges are what make a gesture composable. Persist the layout once, on end, instead of debouncing every frame by hand; pause an expensive child, an iframe or a video while the user drags and resume after; show a snap guide or a dimension badge only while the gesture runs; record a single undo entry per gesture rather than one per pixel.

Each start is paired with exactly one end. A press on a resize handle, on an interactive child (input, button, link, …) or on a `data-no-window-drag` region does not open a drag, so no `onDragStart` fires there either — and a resize never emits drag callbacks, nor the other way round. Unmounting mid-gesture still fires the matching end, so a paused child is never left paused.

## Form Controls

A Window is a regular content surface: any interactive Mantine input works inside it and
keeps its native behavior. In particular a searchable `Select` can be focused, typed into
and filtered — the window only starts dragging when you grab a non-interactive area (or the
header), so form fields never steal the drag and the drag never steals their focus. You can

## Window.Group

Wrap multiple windows in a `Window.Group` to enable coordinated window management. The group provides:

- **Coordinated z-index**: Windows within a group share a stacking context
- **Layout presets**: Snap, tile, and fill layouts via the green tools button in each window header
- **Global actions**: Collapse all, expand all, close all

Each `Window` inside a `Window.Group` must have a unique `id` prop. The group defaults to `withinPortal={false}` (overridable via the `withinPortal` prop) and applies `position: relative` on its container.

<Demo data={demos.group} />

### Tools Button

The green tools button in the window header provides layout options. It is controlled by the `withToolsButton` prop (default: `true`) and is available on every window, even outside a `Window.Group`.

**Without a Group**, the menu shows only single-window actions:

- **Move & Resize**: Snap left, snap right, snap top, snap bottom — positions the current window to fill half of the container or viewport
- **Fill**: Maximizes the current window to fill the entire available area

**Inside a Group**, the menu also shows group-wide actions:

- **Arrange Columns / Rows**: Distributes all visible windows in equal columns or rows
- **Tile**: Arranges all visible windows in an automatic grid
- **Collapse all / Expand all**: Collapses or expands all windows that have `collapsable={true}`. Windows with `collapsable={false}` are skipped.
- **Close all**: Closes all windows in the group

The `onLayoutChange` callback on `Window.Group` notifies you when a group layout is applied.

<Demo data={demos.groupLayout} />

### Layout Presets

Use `defaultLayout` to apply an initial layout when the group mounts. To control the layout externally, use the `groupRef` prop to access the group API and call `applyLayout` programmatically.

<Demo data={demos.layoutPresets} />

### Dynamic Windows

Windows inside a `Window.Group` can be rendered dynamically from an array — for example via `.map()` over a piece of state. Layout presets and group actions wait until the registry is populated and the container is measured, so a layout triggered before all children have mounted is automatically deferred and flushed when everything is ready.

<Demo data={demos.dynamicWindows} />

### Z-index Management

Both `Window.Group` and stand-alone `Window` expose z-index configuration via three props:

- **`initialZIndex`** — starting value for the stacking context. Defaults to `200` when `withinPortal` is `true`, `1` otherwise.
- **`maxZIndex`** — upper bound. When the counter would exceed this value it wraps back to `initialZIndex`, preventing unbounded escalation above modals or menus.
- **`zIndexStrategy`** (`Window.Group` only) — how z-indexes are assigned when a window is focused or registered:
  - `'increment'` (default): a counter monotonically increases. Preserves legacy behavior. Combine with `maxZIndex` to keep values bounded.
  - `'normalize'`: z-indexes are derived from the stacking order and always stay within `initialZIndex .. initialZIndex + N - 1`. Recommended for long-running applications or when Mantine modals and menus are used alongside.

## Headless Hook

`useDragResize` is the engine `Window` is built on, exported so you can put the same geometry on any element: a card, a sticky note, an image, a floating toolbar. Core's `use-floating-window` drags an element; this hook also resizes it, from any edge or corner.

```tsx
import { useDragResize } from '@gfazioli/mantine-window';

function Note() {
  const { ref, position, size, getDragHandleProps, getResizeHandleProps } = useDragResize({
    boundary: 'parent',
    defaultSize: { width: 240, height: 160 },
  });

  return (
    <div
      ref={ref}
      {...getDragHandleProps()}
      style={{ position: 'absolute', left: position.x, top: position.y, ...size }}
    >
      Drag me
      <div {...getResizeHandleProps('bottomRight', { keyboard: true })} className="grip" />
    </div>
  );
}
```

The hook computes, and you render: put `position` on `left` / `top` and `size` on `width` / `height`, with `position: fixed` for `boundary: 'viewport'` (the default) or `position: absolute` in a positioned parent for `boundary: 'parent'`.

**Options.** Everything is optional.

- `position` / `defaultPosition` and `size` / `defaultSize`: controlled or uncontrolled, in pixels, `vw`, `vh` or a percentage of the boundary. The defaults are those of `Window`: `{ x: 20, y: 100 }` and `400 × 400`.
- `minWidth`, `maxWidth`, `minHeight`, `maxHeight`: the same units. The mins default to `250` and `100`, like `Window`'s.
- `boundary`: `'viewport'` or `'parent'`. The element is kept inside it while dragging, and a parent also limits resizing.
- `dragBounds`: a narrower rectangle for the position, in the same units.
- `axis`: `'x'` or `'y'`, to lock dragging to one direction.
- `keepInBounds`: keeps the element inside the boundary. It moves back inside, and shrinks to fit, when the boundary is measured or changes size; `dragBounds` can only narrow the boundary; a pointer resize stops at the viewport edge. `true` by default.
- `resizeStep` and `resizeShiftStep`: the keyboard steps, `10` and `50` pixels by default.
- `onPositionChange` and `onSizeChange`, with pixel values, and `onDragStart`, `onDragEnd`, `onResizeStart` and `onResizeEnd`, at the edges of each gesture.

**Returns.**

- `ref`: for the element that moves.
- `position` and `size`: the current values, in pixels.
- `setPosition` and `setSize`: move or resize it from code, in pixels.
- `isDragging` and `isResizing`: `true` while a pointer gesture runs.
- `boundarySize`: the size of the viewport or of the parent, `0` until it has been measured.
- `getDragHandleProps()`: spread it on the area that starts a drag. A press on an input, a button, a link or a `data-no-window-drag` region never starts one, as in `Window`.
- `getResizeHandleProps(direction, options)`: spread it on a resize handle for `'top'`, `'right'`, `'bottom'`, `'left'` or a corner such as `'bottomRight'`. Pass `{ keyboard: true, label }` to one handle to make it the focusable `separator` described in [Keyboard Resizing](#keyboard-resizing).

Persistence, collapsing, stacking, the title bar and `Window.Group` stay in `Window`: the hook is only the geometry.
